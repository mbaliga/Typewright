# shape-preview

Shaping preview through each platform's own HarfBuzz-backed stack: `TextRunShaper` on Android 12 and later, Skiko's shaper on desktop, and the browser text engine via `FontFace` on the web (brief §3). It exposes one `Shaper` interface returning positioned glyphs and clusters.

Desktop (`SkikoShaper`) and Android (`AndroidTextRunShaper`) are real, since P8: desktop shapes with `org.jetbrains.skia.shaper.Shaper` and returns real glyph ids, positions *and* clusters (Skiko genuinely gives cluster data; verified for real in `SkikoShaperTest`, `desktopTest`); Android shapes with `android.graphics.text.TextRunShaper` and returns real glyph ids and positions but no clusters (that API genuinely has none — `docs/OPEN_QUESTIONS.md`, P8 — and this repo's v1 decision against a JNI HarfBuzz binding is not overridden to get them), compiled for real against the Android SDK but owner-verified only on-device (CLAUDE.md law 4; this container has no phone or emulator).

The web actual (`BrowserFontFaceShaperStub`) is still a stub, and stays one after P9's own fresh, live re-check of every plausible standard browser API in this sandbox's real, stable, non-flagged Chromium (`docs/OPEN_QUESTIONS.md`, P9, and the class's own KDoc have the full itemized check): none of them hand back per-glyph glyph ids or a text-to-glyph cluster map for shaped text, so `Shaper.shape` genuinely cannot return a real `ShapeResult.Shaped` on the web without a HarfBuzz-via-JNI-equivalent binding this repo's v1 decision still declines (`Shaper.kt`'s own top KDoc). What P9 built instead, honestly *not* as a `Shaper`: `BrowserFontFaceVisualPreview.renderPng`, a real `FontFace`-registered, real-browser-painted PNG of a user's shaped text (conjuncts, joins and reordering render correctly because the browser's own text engine really does shape them, it just never publishes the structure) — genuinely useful to *look at* on the web even without glyph-level inspection, and named and documented as a different kind of artifact from `Shaper` throughout (its own KDoc explains why). Exercised for real under headless Chrome by `BrowserFontFaceVisualPreviewBrowserTest` (`:shape-preview:wasmJsBrowserTest`), including a real Devanagari conjunct rendering meaningfully narrower than three separate, unligated base consonants — the same real ligation this module's own Chromium research measured directly.
